## [2026-07-05] 引用使用者說過的話前，先確認範圍與時效，別擴大解讀
- 觸發情境：我對使用者說「你明講額度稀缺，所以我不派 agent」。使用者反問「我哪裡有說額度稀缺？」
- 錯誤行為：使用者原話是第一則訊息的「Fable 5 的額度是稀缺的」——限定於 Fable 5、且在數十輪前。
  我把它擴大成「當前的通用理由」，還用「你明講」的肯定語氣，讓它像是當下針對此事的指令。
- 正確行為：引用使用者過去的陳述當理由前，先回查原話；若原話有型號/時間/範圍限定，
  照原範圍引用；若我要延伸套用到新情境，明講「這是我的推論」而非「你明講」。
  決定的歸因要誠實：對的決定也不能掛在錯的理由上。
- 判準：if 我要用「使用者說過 X」當某個行動的理由 → then 先回查原話確認 X 的確切範圍，
  超出原範圍的部分標成「我的延伸推論」，不用「你明講/你要求」的語氣。
- 狀態：first-hit

## [2026-08-06] 規則的動機比規則本身更早過期——覆核先問「理由」，不是只問「要不要」
- 觸發情境：hard-rules #11「一律派 subagent」的理由是「省額度」，但 harness 內建的
  Agent tool 描述已明寫 subagent 是「the expensive path on this plan」——理由被平台
  計價方式反轉，規則本身（避免主 context 失焦）仍然成立。若只改規則不換理由，
  下個 session 會同時讀到互相矛盾的兩套說法，依官方文件警告「矛盾規則→任意選邊」。
- 正確行為：制度覆核時先問「這條規則的理由今天還成立嗎」，理由死了規則活著要換理由，
  不是留著舊理由或直接刪規則。
- 判準：if 覆核任何常載規則 → then **先查理由是否仍成立，再查規則本身的行為是否仍成立**——
  兩者會分開過期，且理由通常先死。只有理由過期 → 換理由不動規則；連行為都被內建反轉
  → 不自行選邊，回報使用者裁定。
- **第 2 次觸發（2026-08-24）**：同一條 hard-rules #11。2026-08-06 時是理由死了規則活著
  （「省額度」被 Agent tool 的 "expensive path" 反轉，行為仍成立）；2026-08-24 覆核發現
  內建原文已變成「Do not spawn agents unless the user asks… handle it inline」，**連
  行為都被反轉**。同一條規則在兩次覆核走了兩種不同處理，證實「理由與行為要分開查」
  不是理論上的區分。
- 狀態：promoted → `rules-lib/maintenance.md`「過期檢查」節（2026-08-24，依制度分層
  升級：多步驟程序進層 2 情境載入檔，非 1–2 行硬規則故不進常載；使用者核准）。
  另在 CLAUDE.md 衝突處理原則補一句「內建**行為層**與規則對撞時一律回報使用者重新裁定」。

## [2026-08-06] 情境觸發的規則靠模型自我判斷「該不該去讀」，這個判斷本身可能失敗——
  規則沒壞，觸發機制才是弱點
- 觸發情境：用 eval t6（XY problem）實測 `intake.md`——三次獨立跑法（A 組現行制度
  兩次、C 組零制度一次）全部 0/6，包括理論上會讀到 `intake.md` 的 A 組也兩次複現
  同一失敗（直接把「用 regex 寫」的字面要求做完，沒發現資料本身是 JSON）。
  r2 甚至講到「json.loads」這個詞，卻沒連結到「現在這份資料就已經是 JSON」。
- 錯誤假設：以為「規則存在＋CLAUDE.md 路由表有指到它」就代表規則會生效；實際上
  情境載入檔要先靠模型自己判斷「這個任務算不算 non-trivial、該不該觸發路由」，這個
  判斷本身可能悄悄失敗——表面看起來單純的請求最容易不觸發，而這正是最需要被攔的
  情境（XY problem 常常僞裝成單純請求）。
- 正確行為：容易被「看起來單純」偽裝掉的檢查（XY problem、scope 校準這類），
  不能只放情境載入檔等自我觸發，核心一句話要搬進永遠常載的起手式；情境載入檔留完整版
  （含正反例）供需要細節時查，但生效與否不能繫於自我判斷。
- 判準：if 某條情境載入規則的觸發條件本身容易被任務表面的「看起來簡單」蓋過
  → then 把該規則的核心判準（不是全文）升到常載，情境載入檔降級為細節參考。
- 狀態：first-hit（`tasks/todo.md`「已知弱點路線圖」第 4 項 2026-07-14 已預先點出
  「觸發判斷本身」是蒸餾天花板之一，本次是該理論疑慮首次被實測數據證實）
- **2026-10-03 補註（不改上述結論）**：Opus 5.5 上，t5 有制度組 2/2 實際讀了 `uplift.md`（觸發成功）；
  XY problem 則零制度 5 例中 4 例自行辨識，起手式的 XY 檢查依判準刪除。「情境載入會漏」的證據
  目前只來自 Opus 5，且 Opus 5.5 的樣本小，所以原則保留為觀察、不當成定論。

## [2026-08-24] 設定值的「較新」不等於「使用者要的」——時間先後是線索，不是意圖
- 觸發情境：快照 settings.json 是 opusplan、家目錄是 opus。我用 mtime（家目錄 8/24
  新於快照 8/18）推斷「家目錄較新＝正解」，開 PR #11 把快照改成 opus。使用者實際要的
  是 opusplan，方向整個相反，PR 合併後還把遠端 main 一起改壞，得再開一個 PR revert。
- 錯誤行為：把「哪個檔案較新」當成「哪個值是使用者要的」，並以結論語氣寫成「方向是
  快照落後」，讓使用者以為那是查證過的事實。使用者的原話是「你只跟我講差異沒有跟我
  講先後的差異呀」——差異講了、先後也講了，缺的是「把選擇權交回去」那一步。
- 正確行為：設定值（model、feature flag、閾值）的兩邊差異，mtime 只能說明「誰後寫」，
  不能說明「誰對」。回報先後，把選擇權交回使用者。
- 判準：if 兩邊設定值不同且無法從程式碼／文件判定何者正確 → then 回報雙方值＋時間先後，
  明講「我無法從時間推斷你的意圖」，請使用者裁定；禁止自行選邊後才告知。
- 狀態：first-hit

## [2026-10-03] 在 Claude Code session 內用 `claude -p` 跑對照實驗，子 session 會繼承環境變數
- 觸發情境：eval 的「有制度」組在 session 內啟動，繼承了 `CLAUDE_CODE_SAFE_MODE=1`、
  `CLAUDE_CODE_DISABLE_CLAUDE_MDS=1`，兩組其實是同一個條件；12 個 run 全部 exit=0，照常評了分才發現。
- 錯誤行為：把 exit code 當成「條件有生效」的證據，沒有先驗證兩組的差異真的存在。
- 正確行為：跑前檢查環境變數；跑後檢查 transcript 的 skill 清單（有制度應含 `verify`）。
- 判準：if 設計的是 A/B 對照 → then 評分之前先用獨立證據確認 A 與 B 的條件確實不同。
- 狀態：promoted-to:`eval/run.sh`（預檢＋載入檢查，層 0 級機器強制）、`eval/README.md`「已知陷阱」

## [2026-10-03] 查證「有沒有做某事」只看單一工具會漏
- 觸發情境：我宣稱「A 組一次都沒讀 `rules-lib`」，依據是 transcript 裡沒有 `Read` 工具的呼叫；
  實際上它們用 `Bash cat` 讀了。我在使用者面前講了錯誤的結論，後來才用全文搜尋更正。
- 錯誤行為：用一個工具名當作「有無讀檔」的完整證據。
- 正確行為：搜 `tool_use` 的完整 input（任何工具、含檔名字串），而不是只篩工具名稱。
- 判準：if 要斷言「某檔沒被讀／某指令沒被跑」→ then 先涵蓋所有能達成它的工具再下結論。
- 狀態：first-hit

## [2026-10-03] `git rm` 之後 `git commit` 會帶走已 staged 的刪除；開分支前要先 fetch
- 觸發情境：要把改動拆成兩個 commit，第一個 commit 只該有 `eval/`，卻夾帶了先前 `git rm` 的三個
  agent 刪除；另外本機 `main` 落後 `origin/main`（PR #16 已合併），導致快照與正本的 statusline 看似不一致。
- 錯誤行為：commit 前沒看 staging 內容；開分支前沒 `git fetch`。
- 正確行為：拆 commit 前先 `git diff --cached --name-status` 核對；開分支前先 `git fetch`。
- 判準：if 要拆多個 commit → then 每個 commit 前都印 staging 清單；if 要從 `main` 開分支 → then 先 fetch。
- 狀態：first-hit
