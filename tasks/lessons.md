## [2026-07-05] 引用使用者說過的話前，先確認範圍與時效，別擴大解讀
- 觸發情境：我對使用者說「你明講額度稀缺，所以我不派 agent」。使用者反問「我哪裡有說額度稀缺？」
- 錯誤行為：使用者原話是第一則訊息的「Fable 5 的額度是稀缺的」——限定於 Fable 5、且在數十輪前。
  我把它擴大成「當前的通用理由」，還用「你明講」的肯定語氣，讓它像是當下針對此事的指令。
- 正確行為：引用使用者過去的陳述當理由前，先回查原話；若原話有型號/時間/範圍限定，
  照原範圍引用；若我要延伸套用到新情境，明講「這是我的推論」而非「你明講」。
  決定的歸因要誠實：對的決定也不能掛在錯的理由上。
- 判準：if 我要用「使用者說過 X」當某個行動的理由 → then 先回查原話確認 X 的確切範圍，
  超出原範圍的部分標成「我的延伸推論」，不用「你明講/你要求」的語氣。
- 狀態：first-hit

## [2026-08-06] 規則的動機比規則本身更早過期——覆核先問「理由」，不是只問「要不要」
- 觸發情境：hard-rules #11「一律派 subagent」的理由是「省額度」，但 harness 內建的
  Agent tool 描述已明寫 subagent 是「the expensive path on this plan」——理由被平台
  計價方式反轉，規則本身（避免主 context 失焦）仍然成立。若只改規則不換理由，
  下個 session 會同時讀到互相矛盾的兩套說法，依官方文件警告「矛盾規則→任意選邊」。
- 正確行為：制度覆核時先問「這條規則的理由今天還成立嗎」，理由死了規則活著要換理由，
  不是留著舊理由或直接刪規則。
- 判準：if 覆核任何常載規則 → then **先查理由是否仍成立，再查規則本身的行為是否仍成立**——
  兩者會分開過期，且理由通常先死。只有理由過期 → 換理由不動規則；連行為都被內建反轉
  → 不自行選邊，回報使用者裁定。
- **第 2 次觸發（2026-08-24）**：同一條 hard-rules #11。2026-08-06 時是理由死了規則活著
  （「省額度」被 Agent tool 的 "expensive path" 反轉，行為仍成立）；2026-08-24 覆核發現
  內建原文已變成「Do not spawn agents unless the user asks… handle it inline」，**連
  行為都被反轉**。同一條規則在兩次覆核走了兩種不同處理，證實「理由與行為要分開查」
  不是理論上的區分。
- 狀態：promoted → `rules-lib/maintenance.md`「過期檢查」節（2026-08-24，依制度分層
  升級：多步驟程序進層 2 按需檔，非 1–2 行硬規則故不進常載；使用者核准）。
  另在 CLAUDE.md 衝突處理原則補一句「內建**行為層**與規則對撞時一律回報使用者重新裁定」。

## [2026-08-06] 按需觸發的規則靠模型自我判斷「該不該去讀」，這個判斷本身可能失敗——
  規則沒壞，觸發機制才是弱點
- 觸發情境：用 eval t6（XY problem）實測 `intake.md`——三次獨立跑法（A 組現行制度
  兩次、C 組零制度一次）全部 0/6，包括理論上會讀到 `intake.md` 的 A 組也兩次複現
  同一失敗（直接把「用 regex 寫」的字面要求做完，沒發現資料本身是 JSON）。
  r2 甚至講到「json.loads」這個詞，卻沒連結到「現在這份資料就已經是 JSON」。
- 錯誤假設：以為「規則存在＋CLAUDE.md 路由表有指到它」就代表規則會生效；實際上
  按需檔要先靠模型自己判斷「這個任務算不算 non-trivial、該不該觸發路由」，這個
  判斷本身可能悄悄失敗——表面看起來單純的請求最容易不觸發，而這正是最需要被攔的
  情境（XY problem 常常僞裝成單純請求）。
- 正確行為：容易被「看起來單純」偽裝掉的檢查（XY problem、scope 校準這類），
  不能只放按需檔等自我觸發，核心一句話要搬進永遠常載的起手式；按需檔留完整版
  （含正反例）供需要細節時查，但生效與否不能繫於自我判斷。
- 判準：if 某條按需規則的觸發條件本身容易被任務表面的「看起來簡單」蓋過
  → then 把該規則的核心判準（不是全文）升到常載，按需檔降級為細節參考。
- 狀態：first-hit（`tasks/todo.md`「已知弱點路線圖」第 4 項 2026-07-14 已預先點出
  「觸發判斷本身」是蒸餾天花板之一，本次是該理論疑慮首次被實測數據證實）
