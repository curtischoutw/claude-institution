mattpocock × ws 結合工作流

mattpocock 管流程：問什麼、何時切票、何時審、何時停。ws 管專業：誰來寫、誰來審、這個領域怎麼做才對。這一頁把兩邊接起來，每個情境告訴你第一步打什麼、第二步派誰。

/grill-with-docs→ /to-spec→ /to-tickets→ /implement-spec→ ws 語言型 agent 當 implementer→ code-review→ ws 審查型 agent→ /verify→ /retro
白底：mattpocock 的指令 橘底：ws 的 agent 綠底：mattpocock 內部自動呼叫

每個主張都標來源： 事實 我從 SKILL.md、設定檔或工具說明查到的； 建議 我的設計，不是任何一方的官方做法； 未驗證 我沒有實際跑過。

兩邊怎麼接 先選主幹 A 後端功能 B 前端／跨平台 C ML／資料／監控 D 修 bug E 定期保養 42 個 agent 派工範本 不要這樣做 你的制度 未驗證

兩邊怎麼接

先講結論：它們不會自動接起來，要靠你在派工時指名。

mattpocock

流程

問什麼問題、什麼時候寫 spec、怎麼切票、什麼時候審、什麼時候回顧。27 個 skill，沒有一個是某個語言或領域的專家。

ws（claude-code-workflows）

專業

42 個 agent 與一批 skill、command：Python、TypeScript、K8s、ML、資料、安全、效能、無障礙等。它們各有專長，但自己沒有「先問清楚再切票」的紀律。

  • 事實 mattpocock 的 27 個 SKILL.md 從不指定子 agent 的類型。它們只寫「sub-agent」「implementer subagent」「exploration subagent」。所以不會自動用到 ws 的 agent。要用，就在指令後面加一句話指名；沒指名，就由主對話模型依你的 dispatch.md §2 自己挑。
  • 事實 派工時的 model 參數會蓋過 agent 定義裡的 model（Agent tool 說明明載）。ws 有 11 個 agent 定義固定 opus、7 個固定 sonnet（見 docs/plugin-guide.md），你可以在派工時改。dispatch.md §2 也規定派工必明確指定 model。
  • 事實 /to-spec 產出的 spec 有一節 Testing Decisions，寫明要測的 seam。/implement-spec 本來就要求子 agent 靠「脈絡指標」溝通（指向 spec、票、先前 commit）。
  • 建議 把 spec 的 Testing Decisions 當成給所有子 agent 的共同指標：每個 implementer 先讀它，只在那裡列出的 seam 寫測試。這樣不同的 ws agent 不會各自決定測哪裡。

先選主幹：一個功能只選一條

建議 兩邊都有「從需求做到交付」的完整流程（ws 的 feature-development 分 Discovery、Implementation、Delivery 三階段；mattpocock 是 grill → spec → tickets → implement）。疊在同一個功能上，需求釐清和實作會做兩遍。

結合流程 A

後端功能（Python 為例）

主幹：mattpocock。小功能（一個 session 做得完）就跳過第 2、3 步，直接 /implement；dispatch.md §1 的預設本來就是主對話自己做完，不派 agent。

  1. /grill-with-docs先把點子問清楚
    派誰
    預設不派。需要查 repo 現況時，主對話會自己派找事實的子 agent，建議 指定 Explore（dispatch.md §2：要歸納結論用 sonnet）。需要架構取捨的第二意見時，才請 backend-development:backend-development-backend-architect 或 backend-development:event-sourcing-architect 列出選項。
    你要做
    回答每輪問題。架構型 agent 只給選項，事實 grilling 規定「決定是使用者的」。
    產出
    GLOSSARY.md、docs/adr/。
  2. /to-spec寫規格，並把 seam 定死
    派誰
    不派，主對話整理。
    你要做
    確認它提的測試 seam。這是之後所有 implementer 的共同依據。
    產出
    發佈到 tracker 的 spec，含 Testing Decisions。
  3. /to-tickets切成薄切片的票
    派誰
    不派。
    你要做
    檢查粒度和阻擋關係。建議 順便在每張票註明技術領域（後端、前端、資料），第 4 步指名 implementer 時才不用重猜。
  4. /implement-specws agent 當 implementer事實：它派 implementer 子 agent
    派誰
    建議 依票的領域在指令後面指名：
    FastAPI／SQLAlchemy → python-development:python-development-fastapi-pro
    Django／DRF／Celery → python-development:python-development-django-pro
    一般 Python → python-development:python-pro
    Temporal 工作流 → backend-development:temporal-python-pro
    你要做
    在 /implement-spec 後面貼派工範本，並明確指定 model。規格清楚的實作 dispatch.md §2 建議 sonnet；有難度的票才升 opus。
    產出
    一條 integration branch。每張票在自己的 worktree 做，全部完成後 worktree 會被清掉，成果留在 integration branch。

  5. code-review兩軸審查自動
    派誰
    事實 /implement-spec 收尾時自己呼叫，內部派 Standards 與 Spec 兩個子 agent，不指定類型。

    事實 它只有 Standards 和 Spec 兩軸，沒有安全與效能。這兩項在下一步補。
  6. 補上 ws 的專業審查建議
    派誰
    安全 → backend-development:backend-development-security-auditor（定義為 sonnet），再加內建 /security-review
    效能、查詢、併發 → backend-development:backend-development-performance-engineer（定義為 sonnet）
    你要做
    用審查範本派，指定審查 git diff <固定點>...HEAD。審查者沒有參與實作，符合你的硬規則 #12。
  7. /verify宣稱完成前你的制度
    為什麼
    硬規則 #5。mattpocock 的 /implement、/implement-spec 沒有這一步。
  8. 開 PR，然後 /retro
    怎麼做
    說「幫我開 PR」，pr 會自動載入。收尾在 /clear 之前打 /retro。

結合流程 C

ML、資料、微調、監控：ws 當主幹

這些是 ws 有專屬流程指令的領域，mattpocock 沒有對應流程。做法是 mattpocock 前後夾住：先把範圍問清楚、寫死，跑完再審、再回顧。

  1. /grill-with-docs先釐清領域詞彙和目標
    為什麼
    「活躍用戶」「訓練資料」「合格的 checkpoint」這類詞，每個團隊定義不同。把它們寫進 GLOSSARY.md，之後 ws 的多個 agent 才在講同一件事。
    產出
    GLOSSARY.md、必要的 ADR。
  2. /to-spec把範圍和「不做什麼」寫死
    為什麼
    事實 /machine-learning-ops:ml-pipeline 沒有 checkpoint、沒有狀態檔，4 個階段一路跑完，不會停下來等你核准，中斷後也無法接續（docs/plugin-guide.md）。所以範圍必須在它開跑前就寫死，重點寫 Out of Scope 和驗收條件。
    你要做
    確認 spec 的驗收條件是可以用指令判定的。
  3. 記下起點建議
    指令
    git rev-parse HEAD，記下輸出。第 5 步審查要用它當「固定點」，因為 orchestrator 跑完會留下一大批變更。
  4. 打 ws 的專屬流程指令
    怎麼選
    ML 管線 → /machine-learning-ops:ml-pipeline（4 階段，事實 會派 7 個 agent，其中 4 個來自別的 plugin，現在你都裝了）
    資料管線 → /data-engineering:data-pipeline
    資料驅動的功能 → /data-engineering:data-driven-feature（事實 5 階段 16 步驟、4 個 checkpoint，可以在 checkpoint 拿 spec 對照）
    LLM 微調 → /llm-finetuning:finetune（事實 Phase 0–7，以 eval 把關；中間不要插 mattpocock 的流程）
    監控與 SLO → /observability-monitoring:monitor-setup、/observability-monitoring:slo-implement
    三平台同步功能 → /multi-platform-apps:multi-platform
    你要做
    在指令的需求描述裡貼 spec 的 Problem Statement、Solution 和 Out of Scope。
    派誰
    事實 要看是哪個指令。ml-pipeline、data-driven-feature、finetune、multi-platform 會分階段自己派 agent，你不用指名；data-pipeline、monitor-setup、slo-implement 是單一長 prompt，不派子 agent，由主對話照著做。你親手輸入這個指令，符合 dispatch.md §1 的 (c)「使用者明講要派」。
  5. 跑完後審查：code-review
    你要做
    說「review 自 <第 3 步記下的 commit> 以來的變更，spec 在 <spec 位置>」。code-review 是模型可自動載入的 skill，這樣說就會載入。
    為什麼
    事實 orchestrator 沒有 mattpocock 的 Standards／Spec 兩軸審查，這一步補上。Spec 軸正好用第 2 步的 spec 檢查它有沒有超出範圍。
  6. /verify→ /retro
    你要做
    跑得出指令輸出的驗證（測試、pipeline 的 dry run）才算數。收尾 /retro 看 orchestrator 這一輪暴露了哪些環境問題。
結合流程 D

修難纏的 bug 或效能退化

主幹：mattpocock 的 diagnosing-bugs。一眼看得出原因的小 bug 直接改，不必走這張卡。

  1. 說出症狀自動載入 diagnosing-bugs
    你要做
    說「diagnose 這個」或貼錯誤。沒載入就打 /diagnosing-bugs。
  2. 階段 1–2：建紅燈指令並縮小
    派誰
    不派。這是整套流程的核心，需要主對話握住脈絡。
    你要做
    它建不起來時會跟你要環境、log 或錄下的請求檔，盡量給。
  3. 效能退化：先量基準，再二分
    事實
    事實 diagnosing-bugs 的效能分支要求：先建立基準量測（計時、profiler、query plan），再二分；不要靠 log 猜。
    派誰
    建議
    全系統 profiling、tracing → observability-monitoring:observability-monitoring-performance-engineer
    慢查詢、索引、query plan → observability-monitoring:observability-monitoring-database-optimizer
    功能層的效能審查 → backend-development:backend-development-performance-engineer
    ws skill
    python-performance-optimization、python-observability 會依情境自動載入，不用另外打。
  4. 階段 3：看假設清單
    你要做
    它列 3–5 個假設並排序，先給你看。你知道的背景可以直接重排。
    想要第二意見
    建議 把同一份假設清單派給一隻領域型 agent（例如 python-development:python-pro），只問「哪個假設最可疑、為什麼」，符合 dispatch.md (b)「需要 fresh-context 第二意見」。
  5. 階段 4–6：埋點、修、回歸測試、清理
    派誰
    小修補由主對話自己做。建議 修補很大、要換語言型專家時，才用派工範本派 implementer。
    事實
    事實 debug log 都加了 [DEBUG-xxxx] 前綴，最後 grep 清掉。你的 commit_guard.py 在 commit 前只掃少數明確的除錯寫法：console.log(、debugger、breakpoint()、set_trace(、binding.pry、var_dump(、dd(。它刻意不含裸 print，所以帶前綴的 print 或 logger 呼叫它擋不到，清理要靠那條 grep。另外它有 SKIP_DEBUG_GUARD=1 逃生口，內部出錯時放行。
  6. /retro同一個 session 問「什麼能預防它」
    接下來
    如果結論是「這個 codebase 沒有能鎖住這種 bug 的測試位置」，轉到流程 E。

    你的 /debug-protocol（硬規則 #6：同一問題修 2 次沒好就進）和 diagnosing-bugs 目的相近。兩者同時載入時誰先主導，我沒有驗證過。

派工範本

建議 照你的 dispatch.md §6 三要素（目標與動機、驗收條件、回報格式）寫。尖括號 <…> 的地方換成你的內容。

1. 指名 implementer（接在 /implement-spec 後面）

/implement-spec
implementer 請這樣派，每個都明確指定 model：
- 後端票：agent 類型 python-development:python-development-fastapi-pro，model 指定 sonnet
- 前端票：agent 類型 javascript-typescript:typescript-pro，model 指定 sonnet
- 遇到我標了「困難」的票：同一個 agent 類型，model 改指定 opus

每個 implementer 的派工包：
目標與動機：實作 <票的標題>，因為 <spec 的 Problem Statement 一句話>。
範圍與限制：只准動 <票涉及的模組>。先讀 spec 的 Testing Decisions，只在那裡列出的 seam 寫測試，不自行新增 seam。命名用 GLOSSARY.md 的詞；架構用語只用 module、interface、depth、seam、adapter、leverage、locality，不用 service、boundary。
驗收條件：<測試指令> 全綠；票上的驗收項目逐條打勾。
回報格式：結論 ＋ 檔案:行號，10 行內。做不到就直說並回報卡點，不交沒跑過的程式碼。

2. 額外審查（code-review 之後）

派一個 <backend-development:backend-development-security-auditor 或 …performance-engineer>，model 指定 sonnet。

你是沒有參與實作的審查者，只依 spec 與程式碼本身判斷，不看實作者的自述。
審查範圍：git diff <固定點>...HEAD，規格在 <spec 位置>。
重點：<安全：輸入驗證、認證授權、祕密外洩｜效能：N+1 查詢、鎖、逾時>。
回報：verdict（通過／退回）＋問題清單按嚴重度排序，每項附 檔案:行號；沒把握的標「不確定」。10 行內。

不要這樣做

  • 兩條主幹疊在同一個功能上。建議 例如對同一功能先跑 /backend-development:feature-development，又跑 /grill-with-docs → /implement-spec。需求釐清和實作會做兩遍。
  • 讓 tdd-orchestrator、test-automator 自己決定測哪裡。事實 tdd 規定沒經你確認的 seam 不准寫測試；這兩個 agent 的設定是自己管測試策略，會繞過約定。
  • 架構用語不一致。事實 codebase-design 禁用 component、service、API、boundary；architecture-patterns、microservices-patterns 這些 ws skill 正是用 boundary、service、layer 在說話。派 agent 時在 brief 寫明用語。
  • 全指定 opus、又同時派很多個。事實 /implement-spec 會對所有沒被擋住的票平行派 implementer。建議 規格清楚的票用 sonnet，只對困難票升 opus。
  • 沒寫 spec 就直接丟 /machine-learning-ops:ml-pipeline。事實 它不會停下來等你核准。
  • 把架構型 agent 當成決策者。事實 grilling 規定決定歸使用者；架構型 agent 只負責列選項與取捨。
  • 用 ws orchestrator 做完又 /implement 重做一次。先審查（code-review），有缺口再補票。

/implement 最後一步 commitGit 紀律、commit_guard.py事實 /implement 明寫「Commit your work to the current branch」，是無條件 commit。你的規則是「未經要求不 commit／push」，所以兩者直接衝突；你手動打 /implement 算不算「要求」，由你判斷。訊息格式你的規則是 type(scope): description，skill 沒有規定。commit_guard 只掃少數除錯寫法，不管有沒有被要求 commit。

我沒驗證的

下面這些我沒有實際跑過，寫在這裡，不當成已知事實。

  • 未驗證 implementer 指定成 ws agent 之後，它能不能呼叫 tdd skill。agent 的工具清單寫 All tools，但我沒實測。
  • 未驗證 子 agent 是否真的照派工包裡的 seam 約定走，而不是照自己 system prompt 的習慣。
  • 未驗證 code-review 和 Claude Code 內建 /code-review 撞名時，/implement 內部呼叫會解析到哪一個。
  • 未驗證 diagnosing-bugs 與你的 /debug-protocol 同時載入時，誰先主導。
  • 未驗證 tdd 的 mocking 指引和 python-testing-patterns、javascript-testing-patterns 的做法是否矛盾，我沒有逐條比對。
  • 未驗證 verify_gate.py 對「檔案是子 agent 改的、不是主對話改的」會怎麼判斷。
  • 未驗證 不同 ws agent 各自的 system prompt 偏好（例如 fastapi-pro 的慣用寫法）會不會和 spec、GLOSSARY.md 的用語衝突。
