mattpocock-skills 工作流程

這一頁只回答一件事：現在要做的事，第一步打哪個指令、第二步打哪個。每種情境一張步驟卡，照著從 1 做到最後。

/setup-matt-pocock-skills→ /grill-with-docs→ 原型繞道→ /to-spec→ /to-tickets→ /implement→ tdd + code-review→ pr→ /retro
實線：你要手動打的指令 虛線：視情況才做 淺色底：由別的 skill 在內部自動呼叫
示範的一天 A 新功能 B 修 bug C 整理 issue D 大案子 E 定期保養 F 隨時可用 我該用哪個 27 個 skill Phase 交界 注意事項

依據 mattpocock-skills v1.3.1（2026-10-24 安裝）。升版後以各 SKILL.md 為準。

示範的一天

時段只是舉例，不是官方規定。重點是每個時段各用哪個 skill，以及它們的先後順序。

時段在做什麼用哪個
早上整理別人開的 issue，挑出今天要做的/triage → 步驟卡 C
上午把一張標好 ready-for-agent 的票做完/implement → 步驟卡 C 的第 4 步
中午後開始一個新功能：先想清楚、再寫規格、再切票/grill-with-docs → /to-spec → /to-tickets → 步驟卡 A
下午一張票一個 session 地做/implement，票與票之間 /clear
隨時撞到難纏的 bug步驟卡 B（diagnosing-bugs）
收工前回顧這個 session，改善 agent 的環境/retro（要在 /clear 之前）
每隔幾天掃一次 codebase 找可重構的地方/improve-codebase-architecture → 步驟卡 E
步驟卡 A

做一個新功能（最常用）

什麼時候用：你有個點子，要把它做出來，而且有 repo 可以留紀錄。

  1. /setup-matt-pocock-skills每個 repo 只做一次手動
    你要做
    回答三題：issue 放哪（GitHub／GitLab／本機 .scratch/）、triage 標籤要不要用預設（建議用）、詞彙表放哪（單一 context 即可）。
    產出
    repo 的 CLAUDE.md 多一段 ## Agent skills，以及 docs/agents/*.md。
    沒做會怎樣
    /to-spec、/to-tickets、/triage 會叫你先來做這步。
  2. /grill-with-docs先被拷問，把點子問到清楚手動
    你要做
    用一兩句話講點子。之後它每一輪列出編號問題，每題附推薦答案；你回「全部接受」或「Q2 改成…」。重複到它說沒有問題了，你再明確告訴它「達成共識」。
    產出
    討論中釐清的詞會當場寫進 GLOSSARY.md，難以回頭的決定寫成 docs/adr/NNNN-*.md。
    它內部呼叫
    自動 grilling 與 domain-modeling。

    從這一步到第 5 步的 /to-tickets，盡量留在同一個 session，不要 /clear。

  3. 有問題只能跑起來才答得出來？先做原型視情況
    什麼情況
    狀態模型對不對、商業邏輯順不順、UI 該長什麼樣，光講講不出答案。
    做法
    ① /handoff 把目前脈絡存成檔。 ② 開新 session，說「照這份交接檔做個原型，回答這個問題」，prototype 會自動載入。 ③ 原型答完，/handoff 把結論帶回原本的 session。
    原型的樣子
    邏輯問題 → 一個你雙擊就能玩的 HTML 檔；UI 問題 → 同一路由上多個風格迥異的版本，用網址參數切換。
  4. 判斷：一個 session 做得完嗎？
    做得完（小功能）直接跳到第 6 步 /implement，不用寫 spec 和切票。
    做不完（跨多個 session）繼續第 5 步：先 /to-spec，再 /to-tickets。
  5. /to-spec/to-tickets把討論變成規格，再切成票手動
    /to-spec
    不再訪談你，只把剛才的對話整理成 spec。唯一要你回答的是「要測試的 seam 對不對」（它會建議盡量只有一個、而且愈高層愈好）。確認後發佈到 tracker，貼上 ready-for-agent。
    /to-tickets
    切成「薄切片」票，每張都穿過所有層、自己能驗證、並標明被哪些票擋住。它會把清單給你看，問你粒度對不對、阻擋關係對不對、要不要合併或再拆；你同意才發佈。
    產出
    GitHub／GitLab：一票一個 issue，用原生阻擋關係。本機：.scratch/<feature>/issues/01-*.md、02-*.md…，blockers 先編號。
  6. /implement開始寫手動
    你要做
    多張票時，一張票一個 session：/implement <票的編號或網址>，做完 /clear，再做下一張（從沒被擋住的票開始）。單一小功能就在原 session 直接 /implement。
    它內部依序做
    自動 tdd：先跟你確認要測的 seam，再一次一個「紅 → 綠」切片； 中途定期跑型別檢查與單檔測試，最後跑一次完整測試； 自動 code-review 審 diff； 最後 commit 到目前的 branch。
    你要盯的一點
    寫第一個測試之前，它會把「要測哪些 seam」列給你。這是你唯一必須回答的地方，別直接略過。
    想自己一張一張驅動用 /implement，如上。
    想整份 spec 一次叫它跑完用 /implement-spec：它在一條 integration branch 上，派多個子 agent 平行做互不阻擋的票，最後審一次、開 draft PR。
  7. /verify宣稱完成前（你自己制度裡的）你的制度
    為什麼放這裡
    你的硬規則 #5 要求宣稱完成前走 /verify 並附實際指令輸出。mattpocock 的 /implement 沒有這一步，需要你自己補。
  8. 開 PR：叫 Claude 開，不用另外打指令自動
    怎麼做
    說「幫我開 PR」。Claude 寫 PR 本文時會自己載入 pr skill。
    本文長相
    Summary（最小而能說清楚的圖：偽碼、呼叫樹、檔案樹或 diff 草圖）→ Evidence（改前改後對照）→ Merge Danger（單向門或雙向門，加爆炸半徑）。
  9. /retro收尾：改善環境，不是改程式碼手動
    你要做
    在這個 session 還沒 /clear 之前打。已經清掉的話，指定那個 session 的 log。
    產出
    依嚴重度排序的建議：導覽指標、可以自動化的檢查（優先做成 lint／hook／CI）、該給 reviewer 的新規則、太長的 CLAUDE.md 該如何瘦身。
步驟卡 B

修一個難纏的 bug

什麼時候用：壞掉、拋錯、間歇性失敗、突然變慢。小到一眼看得出來的就直接改，不必走這張卡。

  1. 把症狀告訴 Claude自動載入 diagnosing-bugs
    你要做
    說「diagnose 這個」或貼錯誤。沒自動載入就打 /diagnosing-bugs。
  2. 階段 1–2：它先建「紅燈指令」，再縮小
    它做
    找一個它已經跑過、能在「這個 bug」上變紅、結果穩定、幾秒就跑完的指令。沒有這個指令，不准進入猜原因。再把重現步驟逐項砍到每一項都是必要的。
    你要做
    它建不起來時會明講，並跟你要環境權限、log 或錄下的請求檔。盡量給。
  3. 階段 3：看它的假設清單
    你要做
    它列出 3–5 個假設並排序，先給你看。你知道的背景（「昨天剛改過 X」）可以直接重排它們。你不在場時它會照自己的排序繼續。
  4. 階段 4–6：埋點、修、回歸測試、清理
    它做
    每個 debug log 都加唯一前綴（例如 [DEBUG-a4f2]），最後一條 grep 清乾淨；先寫回歸測試再修；在 commit 訊息寫下確認的原因。
    特別留意
    如果找不到一個「能真實重現這個 bug」的測試位置，它會把這件事記為發現，而不是硬寫一個沒意義的測試。
  5. /retro同一個 session 問「什麼能預防它」手動
    接下來
    如果結論是「這個 codebase 沒有好的測試位置」，就接 /improve-codebase-architecture（步驟卡 E）。
步驟卡 C

整理別人開的 issue

什麼時候用：bug 回報、功能需求堆在那邊。只用在「不是你自己用 /to-tickets 產生的」issue，後者本來就是 agent 可直接做的。

  1. /triage看有哪些要處理手動
    你要做
    用平常的話下指令，例如「Show me anything that needs my attention」。它列三堆，由舊到新：從沒處理過的、needs-triage、以及回報人有新回覆的 needs-info。
  2. 挑一張：「看一下 #42」
    它做
    讀完整串留言、查 codebase 是否早就有這功能、查 .out-of-scope/ 是否曾被拒絕、實際重現回報的問題，然後給你分類和狀態建議。
    你要做
    同意或改它的建議。需要把需求問清楚時，它會自動接上拷問。
  3. 套用結果
    狀態
    ready-for-agent 貼 agent brief；needs-info 貼具體的提問；wontfix 帶理由關閉（被拒絕的功能需求會記進 .out-of-scope/）。
    留言規定
    它在 tracker 上貼的每則留言開頭都有一行「由 AI 在 triage 時產生」的聲明。

    這步會直接在 tracker 上貼留言、改標籤、關閉 issue，別人看得到。

  4. /implement做標了 ready-for-agent 的票手動
    你要做
    /implement #42。它會先抓下票、說出標題，再接步驟卡 A 第 6 步的流程。
步驟卡 D

一個 session 裝不下的大案子

什麼時候用：新專案，或大到方向都還模糊的功能。範圍明確的功能不要用，會浪費力氣。

  1. /wayfinder畫地圖，這個 session 到此為止手動
    你要做
    講出大方向。它先用拷問幫你「命名終點」，再用拷問找出現在就能問的決策，最後在 tracker 建一張地圖和一批「決策票」。
    它不做
    不解任何一張票，也不寫程式。

    它的 research 子 agent 會把查到的資料放在 research/<name> 分支並 push 到遠端，不開 PR。

  2. /wayfinder <地圖網址或編號>每個新 session 解一張票手動
    你要做
    不指定票的話，它會從沒被擋住的票挑第一張並先認領。依票的類型：research 由子 agent 查資料；prototype 和 grilling 要你在場回答；task 是先做某件事才能做決定。解完就貼結論、關票、更新地圖。
    規則
    一個 session 只解一張票（research 票除外）。你可以同時開幾個 session 各解不同票。
  3. /to-spec地圖清楚後，在這裡接回主流程手動
    為什麼不直接 /implement
    /to-spec 會把地圖上互相連結的決策整合成一份可建置的計畫，直接跳過會丟掉那些細節。
    接下來
    /to-tickets → /implement，同步驟卡 A 的第 5、6 步。
步驟卡 E

定期保養 codebase

什麼時候用：作者建議每隔幾天跑一次。它找候選，不會幫你解開已經纏在一起的舊程式。

  1. /improve-codebase-architecture手動
    你要做
    可以直接指定方向（某個模組、某個痛點）；沒指定的話它看 git 歷史找最常變動的地方。
    產出
    一份視覺化 HTML 報告寫到系統暫存目錄（不進 repo），每個候選有改前改後圖和建議強度，最後有「最推薦哪個」。報告會自動開啟。
  2. 選一個候選
    你要做
    它問「想探索哪個」，你選一個。此時它自動接上拷問，聊限制、依賴、深化後的模組長什麼樣、哪些測試能留下。必要時更新 GLOSSARY.md，你否決時它會問要不要記成 ADR。
  3. 把結果帶進步驟卡 A
    接下來
    從 /grill-with-docs 開始，或規模小就直接 /implement。
步驟卡 F

隨時可以插進任何流程的工具

它們不屬於哪一條流程，需要時直接打。

一個階段做完了，接下來清掉還是壓縮？

「階段」就是你心想「好，這段做完了」的時候，例如拷問結束、實作結束。只在交界處決定，中途就繼續做。從上往下問，第一個答案是「是」就停。

順序問題答案是「是」就
1下一階段需要這一階段的原始對話，或剩下的空間（約 150k tokens）還夠？繼續，什麼都不做。拷問接實作就是標準的「是」。
2這個 session 裡的東西，對下一步全部沒用？/clear
3要換 harness、換目錄、給同事，或階段中途想分出一個支線？/handoff
4任務夠小，你不在場也能自己跑完？（自動 review 是典型）丟給子 agent
5以上皆否/compact，並帶一句下一步要做什麼，例如 /compact 接下來要 QA 這一塊

除了「繼續」，其他每一種都會把原始對話換成摘要，會有資訊損失。所以第 1 題問「能不能繼續」。這些都是判斷題，同一個交界在不同天可能走不同路。

用之前要知道的事

只列事實。要不要調整你的制度，是另外的決定。

  • 撞名：code-review 和 Claude Code 內建的 /code-review 同名。要用 plugin 版請打 /mattpocock-skills:code-review。/implement 內部呼叫 code-review 時會用到哪一個，我沒有驗證過。
