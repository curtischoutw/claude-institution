## 一句話結論

以日常任務組合估計，「Opus＋本制度」約可達 Fable 產出品質的 **~85%**（推測，未經
2026-08-06 實測驗證，見上方警示）；剩餘缺口是推理深度與品味，不是流程——
再堆規則補不了，且會因常載膨脹倒扣。

## 制度起作用的機制

制度不讓模型「變聰明」，而是做兩件事：

1. **把單次內部直覺換成多次、可檢驗、可回溯的外部流程**（uplift.md 的核心主張）：
   先寫判準再作答、多答案評審、對抗自查、結論必附可證偽檢驗。
2. **堵住弱模型最傷的失效模式**：假完成（done-check）、自驗自查（dispatch 驗證節）、
   亂槍打鳥除錯（debug-protocol）、scope 蔓延（intake + hard-rules #7）、
   沉默假設（code-standards）。模型間「實際產出品質差距」的大宗來自這些失效模式，
   而非單步推理能力——堵住它們，差距縮小大半。

## 分級估計（以「最終產出品質達到 Fable 水準的比例」計）

| 任務類型 | 無制度的 Opus | 有制度的 Opus | 主要起作用的制度件 |
|---|---|---|---|
| 例行/機械（批次改檔、小 bug、boilerplate） | ~90% | **~95%+** | done-check 防粗心 |
| 中等（新功能、重構、一般除錯） | ~70–80% | **~85–90%** | intake、design-heuristics、debug 2.5、done-check |
| 高難（難根因、架構取捨、模糊規格） | ~55–65% | **~65–75%** | uplift 方法 1–4 滿配（token 成本 2–4 倍） |
| **加權日常組合** | | **~85%**（高難佔比高則往 80 靠） | |

## 制度補不了的剩餘缺口（誠實條款：這些是品味與推理深度）

1. **假設空間廣度**：難根因下，Fable 一輪能同時持有更多互斥假設並注意到微弱矛盾。
2. **沒說出口的問題**：從描述中看出使用者「真正該擔心但沒問的事」。
   ~~intake.md 補了最常見的 XY 形態，補不了長尾。~~（**2026-08-06 修正**：這句話
   本身被實測推翻——三次獨立測試（含理論上會讀到 `intake.md` 的情境）連「最常見
   的 XY 形態」都沒補到，問題不是內容不夠好，是情境載入檔的自我觸發機制不可靠。已把
   核心判準搬進 CLAUDE.md 常載起手式，這個缺口目前**降級為「機制修正後待重新驗證」**，
   不是「制度補不了的本質缺口」。）
3. **一次到位的設計品味**：制度用「迭代＋外部審查」換結果，換不到一次到位。
4. **元判斷**：知道「這條規則此刻不適用」。規則越多此項越傷——這是常載規則
   必須節制的根本原因（原引用 diagnosis.md 第 2 名耗損源，該檔 2026-08-06 已刪並
   併入 `rules-lib/maintenance.md`「加常載規則前必答兩題」節）。

缺口 1–4 的制度化補償路徑只有一條：dispatch.md 的 Fable 窄閥
（高風險判斷＋opus 兩輪失敗 → 提議派一次 fable 仲裁，經使用者同意才派）。

## 2026-08-06 實測結果（t3–t6，Opus 5，A 現行制度 vs C `--safe-mode` 零制度）

**這不是「Opus＋制度 vs Fable」的驗證，是「Opus 有無制度」的獨立子實驗**，完全沒有
Fable 參與。完整記錄見 `eval/results/2026-08-06-opus5-{有制度,零制度}.md`。

| 題 | 對應原表格分類 | A 現行制度 | C 零制度 | 結論 |
|---|---|---|---|---|
| t3 確定性 bug | 例行/機械 | 6/6 | 6/6 | 無差異——與原表格「~90%→~95%+」的方向一致（差距已很小），但實測看不出制度增益 |
| t4 間歇性 bug | 中等 | 6/6 | 6/6 | 無差異 |
| t5 架構取捨 | 高難 | ~4/6 | ~1/6 | **制度有實質增益**，方向與原表格「~55–65%→~65–75%」一致 |
| t6 XY problem | （原表格未單列，屬缺口 2「沒說出口的問題」） | 0/6、0/6（兩次） | 0/6 | **制度未發揮設計目的**，三次全部落入同一陷阱，且原因是機制不是內容（見上方缺口 2 修正） |

**對原表格的校正**：例行/機械與中等兩類的「有制度 vs 無制度」差距，實測比原推測更小
（至少在 t3/t4 這兩個具體任務上是 0 差距，不是原表估計的 ~5–15 個百分點）；高難類
的方向性支持成立。t6 揭露的是原表格完全沒預期到的失效模式——不是「補不到長尾」，
是「補不到最常見的情況」，且是機制性的（情境觸發不可靠），不是內容深度不夠。

## Token 平衡三條線

1. 新規則一律層 0（hook）或層 2（情境載入檔），不進常載；常載合計上限 200 行
   （2026-08-06 由 500 行下修，比照官方 CLAUDE.md 建議上限；現況約 130 行）。
2. uplift 高強度方法照風險分級 gate：多答案評審只給「影響 ≥1 天」的決策。
   85% 是性價比甜蜜點——每往上擠一分，邊際 token 成本遞增。
3. eval 只在制度改版時跑，不進日常循環。

## 可證偽性與更新方式

- 本檔每個 % 的檢驗方式：跑 `../eval/` 六題，同題比對「Opus 無制度 / Opus 有制度 /
  （可選）Fable」的 checklist 得分。得分比與本檔估計差 >10 個百分點 → 回來改本檔，
  並在下方 Changelog 記錄「當時推測 vs 實測」。
- 制度重大改版後重跑 eval，把增益歸因到具體制度件，砍掉沒有增益的規則
  （規則只加不刪是耗損源，原引用 diagnosis.md，該檔已刪並併入 maintenance.md）。
