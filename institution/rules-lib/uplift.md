# 判斷力增強協定：便宜模型如何逼近高階判斷

## 核心原則

你不需要「更聰明」，你需要「不讓單次直覺定生死」。以下每個方法都在做同一件事：
把一次性的內部判斷，換成多次、可檢驗、可回溯的外部流程。

## 方法 1：先寫判準，再作答（防事後合理化）

**時機**：任何要在多個方案中選一個的時刻。
**步驟**：
1. 還沒想方案之前，先寫下「好答案的 3–5 條判準」（可驗證的，不是「要優雅」）。
2. 產出方案後，逐條打分，分數表跟著結論一起交。
3. 若發現自己想改判準遷就方案 → 這就是偏誤警報，停下重想。

- 正例：選資料庫前先寫「判準：單機可跑／查詢延遲 <10ms／團隊已會維護」，再比方案。
- 反例：先喜歡上 PostgreSQL，再回頭列一堆它剛好符合的優點。

## 方法 2：多答案評審擇優（用多樣性補判斷）

**時機**：高風險且答案空間大（架構、根因分析、制度設計）。
**步驟**：
1. 派 2–3 個 fresh-context subagent 解同一題，prompt 明確要求走不同路線
   （例：「一個以簡單優先，一個以擴展性優先」）。
2. 收齊後列「分歧點清單」——他們不一致的地方就是問題的真正難點。
3. 只針對分歧點做判斷（可再派一個評審 agent），一致的部分直接採納。
**預算判準**：if 決策影響 ≥1 天工作量 → then 值得多花 2 個 subagent。
**先試內建**：純程式碼層面的第二意見先用 `/code-review`（分工見 `dispatch.md` §3）；
本方法用在「答案空間大、需要不同路線」的設計題，內建無等價。

## 方法 3：對抗自查（強制紅隊回合）

**時機**：每個重要產出交付前（done-check 之後、回報之前）。
**步驟**：
1. 切換立場自問：「假設這個方案 3 個月後出了大問題，最可能是什麼？」寫出前 3 名。
2. 每一名花一分鐘找證據：能排除就寫排除理由，不能排除就寫進回報的風險欄。
3. 找不到任何一個像樣的失敗模式 → 你還不夠了解這個方案，回去讀。

- 正例：「風險第 1 名：快取失效時雪崩打爆 DB。驗證：加了 jitter，見 cache.py:42。」
- 反例：紅隊回合寫「應該沒什麼問題」→ 等於沒做，重做。

**先試內建**：`/code-review`、`/simplify`、`/security-review` 已覆蓋大部分鏡頭；
何時改派 skeptic／red-team／simplifier 三個 agent，判準見 `dispatch.md` §3。

## 方法 4：結論具體化強制

**規則**：任何結論必須附「一個能證偽它的檢驗」。寫不出檢驗方式的結論，
一律降級標成「假設」，不准當結論交付。

- 正例：「瓶頸在 N+1 查詢（檢驗：開 SQL log 數同一請求的查詢次數，>50 即證實）」。
- 反例：「效能不佳主要是架構問題」——不可檢驗，這是感想不是結論。

## 方法 5：重大決策日誌（讓判斷可回溯、可學習）

**時機**：影響 ≥1 天工作量、或未來很難回頭的決策。
**格式**（記在 tasks/todo.md 的決策節或獨立 decisions.md）：
```
[日期] 決策：<選了什麼>
放棄：<替代方案 A/B 與各自被放棄的原因>
證據：<支持此選擇的事實>
推翻條件：<出現什麼訊號代表選錯了，該回頭>
```
價值：三個月後發現選錯時，能分清「當時資訊不足」還是「當時判斷錯」——後者進 /lesson。

## 方法 6：問題重述（最便宜的糾錯時點）

**時機**：接到任何非平凡任務，動手前。
**步驟**：用自己的話重述問題 + 列出使用者沒明說的隱含約束（≤5 條）+ 一句話說明
「做完後世界有什麼不同」。重述不出來 = 還沒理解，去讀相關檔案而不是開始寫。

## 使用強度分級（別把每件事都上滿配）

| 任務風險 | 用哪些方法 |
|---|---|
| 例行小事（改文案、小 bug） | 都不用，直接做＋/done-check |
| 中風險（新功能、重構） | 方法 6 + 3 + 4 |
| 高風險（架構、制度、難根因） | 全部，含方法 2 的多答案評審 |

## 邊界

本協定補的是「流程性判斷」（防偏誤、防漏想、防過度自信），補不了品味與模糊題——
遇到後者照 judgment.md 誠實條款處理。
