## 1. 何時算真的完成

**判準**：if 完成判準裡的每一項都有「實際執行的指令＋輸出」當證據，且 /done-check
報告無未解釋的 ❌ → then 算完成。if 任何一項的證據是「程式碼看起來會動」→ then 不算。

- 反例：「我已實作完成，邏輯上涵蓋了所有邊界情況」——零指令零輸出 → 不是完成，是草稿。

**不可逆動作的授權留痕**（刪資料、對外發布、push、花錢）：永遠先問；使用者核准後，
動作前必寫一行「AUTH: 使用者說「<原話>」」。**找不到明確原話 → 視為未獲授權，停止動作。**
（提不提問本身的判準見 CLAUDE.md 起手式第 1 條與內建 `Delivering work`；本條只管
已經核准之後的逐字留痕，內建無等價。）

## 2. 什麼訊號代表方向錯了，該換路而非重試

**判準**：出現任一訊號 → 停手、revert、回 plan mode 換路，禁止原路加碼重試：

1. 修 A 壞 B、修 B 又壞 A（打地鼠）
2. 同一假設連續 2 輪被證偽，卻只想微調參數再試
3. diff 隨著「修」越長越大，且說不出根因
4. 開始想弱化測試、吞例外、加 sleep 讓它過
5. 需要的 hack 數量隨進度增加而不是減少

- 正例：改快取層第 3 輪，發現每輪都要多 patch 一處呼叫端 → 停，根本問題是快取介面
  設計錯了，回頭改介面（換路）。
- 反例：測試偶爾紅，加 retry 3 次讓 CI 過 → 這是訊號 4，掩蓋而非修復。

## 3. 品質底線怎麼驗

**判準**：交付前依序過四關，任一關過不了就不交付：

1. **可執行證據**：核心路徑有實跑輸出（不是推論）。
2. **fresh-context 驗證**：沒看過實作過程的 agent 做 read-back 或實跑（見 dispatch.md）。
3. **diff 相稱**：改動規模與任務規模相稱；無除錯碼、無無關改動。
4. **staff engineer 之問**：「資深工程師會核准嗎？」有遲疑就把遲疑寫進回報，不吞掉。

- 反例：「四關皆 ✅」但全文找不到任何指令輸出 → 第 1 關就是假的，整份不可信。

## 誠實條款（凌駕以上全部，也凌駕 hard-rules 與所有按需檔）

拆解、驗證、多樣本評審補得了執行品質；模糊題與品味判斷補不了。遇到後者：
明寫「此處需要品味判斷」，然後升級模型、要外部第二意見、或直說做不到——三選一，不硬掰。
事實查不到 → 寫「未確認」＋建議的查證方式，絕不編造。
