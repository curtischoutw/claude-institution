## 原則：派工是例外

預設主對話自己做完（與內建 Agent tool 說明「Do not spawn agents unless the user asks…
handle it inline」同向）。派工唯一站得住的理由是**中間輸出會淹沒主 context**，
不是省額度，也不是「任務看起來有好幾個面向」。命中 hard-rules #11 的 (a)(b)(c) 才派。

真的要派時：

- 互相獨立的任務在同一則訊息**平行派出**，不串行等。
- **必顯式指定 `model`**，不留空繼承——留空會繼承主對話模型（實務上曾讓 Explore 默默
  跑在 fable 上）。
- 任務描述（使用者可見的 description）標明 agent 類型與模型，例：「掃描 repo（Explore+haiku）」，
  讓使用者一眼看見每筆派工用了哪隻模型。

## 可用型號與參數

以**當前 harness 的 Agent 工具 schema 與環境宣告**為準，不憑本檔或記憶填寫（hard-rules #8）。
拿不準參數格式時派 claude-code-guide 查官方文件，不猜。

任務越唯讀／機械化（搜尋、摘要、批次改檔）越用便宜模型；越需要判斷／仲裁（架構決策、
難根因、多答案評審）越用貴模型。拿不準用哪級 → 先派便宜的，照升降級路徑走。

## 交辦三要素（缺一不發）

1. **目標與動機**：做什麼＋為什麼（讓 subagent 能自行取捨細節）。
2. **驗收條件**：可驗證的完成判準（能寫成指令最好）。
3. **回報格式**：長度上限與結構。

## 通用派工包（填空，不要即興寫）

```
目標與動機：<做什麼>，因為 <為什麼>。
範圍與限制：只准動 <檔案範圍>；遵守 ~/.claude/rules/ 下的常載規則；
  不確定的設計決策先用最簡單解並在回報標註 ASSUMPTION。
驗收條件：<可機械判定，例如「pytest tests/x.py 全綠」>，不是「能動就好」。
回報格式：結論 + 「檔案:行號」；長產物存到 <路徑> 後只回路徑＋3 行摘要。上限 N 行。
查不到／做不到就直說並回報卡點，禁止編造，禁止交出沒跑過的程式碼。
```

四種常見任務在此基礎上各加一句：

- **搜尋**（Explore+haiku）：加「也要檢查 <別名/舊名/字串引用等變形>；找不到就回
  『無結果』並列出搜過的 pattern」。
- **實作**（general-purpose+sonnet）：加「規格逐條列出；新增測試 <名稱> 且全綠」。
- **重構**（general-purpose+sonnet）：加「**不變式**（絕不能變的行為，例如現有測試不改
  內容且全綠、公開 API 簽名不變）；**先跑 <測試指令> 記錄基線**再小步改，每步重跑；
  任何一步變紅且 2 次內修不回 → 立即 revert 全部並回報，不要硬推」。
- **研究**（+haiku；需權衡結論時 sonnet）：加「來源優先序：官方文件 > 原始碼 > 其他；
  每個結論附出處（URL 或 檔案:行號）；區分事實與推測；**禁止用訓練記憶充當查證結果**」。
- **審查**（+opus）：加「你是沒有參與實作的審查者，只依規格與程式碼本身判斷（**不給
  實作者自述**）；verdict（通過/退回）＋問題清單按嚴重度排序；沒把握的標『不確定』」。

## 升降級路徑

- **haiku 錯 1 次** → 同任務升 sonnet 重派（附 haiku 的錯誤輸出當反例）。
- **sonnet 同一子任務連錯 2 次** → 升 opus，附完整失敗軌跡（兩次的輸入、輸出、錯在哪）。
- **opus 解出模式後** → 把解法寫成明確步驟，降回 sonnet/haiku 批次套用到其餘同類項。
- **同一子任務最多重試 2 輪**（升級也算輪）：仍失敗 → 停，向使用者回報事實、已排除
  假設、卡點。
- 層級區分（別跟除錯搞混）：本節的「輪」指指揮官重新交辦 subagent 的次數；
  hard-rules #6 的「2 次沒好進 /debug-protocol、第 3 次停手 revert」指單一 agent
  在自己 context 內的除錯修改次數。兩者各自計數，互不抵扣。
- **fable**：原則不派，僅使用者明說才用；用後回報實際消耗。若指揮官本身就是 fable，
  階梯倒轉為只降不升，opus 兩輪失敗由指揮官親自拍板。
- **反例（量大不等於需要升級）**：要改 40 個檔案的 import 路徑，覺得「量大很難」就升
  opus → 錯，這是機械活，haiku 批次做＋抽查即可。

## 驗證（不自驗）

修改者永不擔任自己產出的唯一驗證者。驗證一律派 **fresh-context** agent（乾淨 context，
沒看過實作過程），且驗證 prompt 只給規格、不給實作者的自述：

| 產出類型 | 驗證方式 |
|---|---|
| 檔案/文件 | read-back：叫它讀檔，回答「是否完整、與規格哪裡不符、哪句弱模型會誤讀」 |
| 程式碼 | 實跑：跑測試或走主流程，貼輸出；不接受「看起來正確」 |
| 高風險判斷 | 第二意見：同題派 2 個 agent 各自作答比對分歧；或多答案評審擇優 |

驗證 agent 的回報也遵守回報合約：結論 + 檔案:行號 + 修正建議，不整篇重抄。
