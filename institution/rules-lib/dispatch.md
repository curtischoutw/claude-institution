## §1 派不派：先過這道閘門

預設**主對話自己做完**，與內建 Agent tool 說明同向（「Do not spawn agents unless the user
asks… handle it inline」）。逐條檢查，命中任一條才往下走 §2；三條都沒中就自己做：

- [ ] **(a) 中間輸出會淹沒主 context**——掃 repo、位置不明的大範圍搜尋、批次讀十幾個檔。
- [ ] **(b) 需要 fresh-context 第二意見**——見 §7，修改者不得自驗。
- [ ] **(c) 使用者明講要派。**

站不住的理由（出現這些就是還在 §1，不准往下）：省額度、任務看起來有好幾個面向、
量大、覺得自己做很慢。

## §2 情境 → agent 類型 ＋ 模型

**型號與 agent 類型清單以當前 Agent tool schema 的 `model` enum 與環境宣告為準**
（hard-rules #8：查得到寫實際值，不憑記憶）。下表是**選擇原則**；schema 若無該型號，
照能力階梯就近對應。

| 情境 | agent 類型 | 模型 | 為什麼 |
|---|---|---|---|
| 掃 repo、位置不明的大範圍搜尋、批次讀十幾個檔 | `Explore` | `haiku` | 唯讀、機械、量大 |
| 要跨多處歸納出結論的探索（不只是找到位置） | `Explore` | `sonnet` | 需要判斷 |
| 規格清楚的實作 | `general-purpose` | `sonnet` | |
| 重構（有不變式、有基線測試） | `general-purpose` | `sonnet` | |
| 事實查證研究 | `general-purpose` | `haiku`；需權衡結論時 `sonnet` | |
| 查 Claude Code／Agent SDK／Claude API 的官方行為 | `claude-code-guide` | 依該 agent 定義 | 專職 agent，勝過自己猜 |
| 設計實作策略、架構取捨 | `Plan` | `opus` | 判斷密集 |
| 重大結論要三個獨立 verdict | `skeptic`／`red-team`／`simplifier` | `opus` | 見 §3 |
| fresh-context 驗證 | `general-purpose` | 文件 read-back `haiku`；程式碼實跑 `sonnet` | 見 §7 |

一句話原則：**越唯讀、越機械化就越便宜；越需要判斷、越需要仲裁就越貴。**
拿不準用哪級 → 先派便宜的，照 §5 升降級。

派工時另外三條：

- 互相獨立的任務在同一則訊息**平行派出**，不串行等。
- **必明確指定 `model`**，不留空繼承——留空會繼承主對話模型（實務上曾讓 Explore 默默跑在 fable 上）。
- 任務描述（使用者可見的 description）標明 agent 類型與模型，例：「掃描 repo（Explore+haiku）」，
  讓使用者一眼看見每筆派工用了哪隻模型。

## §3 內建指令 vs 自製 agent

**先用內建**，它們已覆蓋大部分審查鏡頭：

| 要審什麼 | 用什麼 |
|---|---|
| 程式碼正確性 | `/code-review` |
| 過度工程、可簡化處 | `/simplify` |
| 安全問題 | `/security-review` |

**只有需要三個獨立 verdict 各自表態時**，才派 `skeptic`／`red-team`／`simplifier`。
它們比內建多的東西只有兩樣：固定 YAML verdict 信封，以及「不得為了判 REFUTED 而編造
牽強反例」的約束。除此之外沒有理由派它們。

## §4 主對話模型：opusplan、fast mode、fable

`~/.claude/settings.json` 目前設 `"model": "opusplan"`、`"effortLevel": "high"`。

**`opusplan`**（官方定義）：plan mode 用 `opus`，切到執行時自動換 `sonnet`。
所以「先進 plan mode 想清楚，再退出執行」不只是流程紀律，也直接決定了哪隻模型在想、
哪隻模型在寫。要讓 opus 親自執行（而非只負責規劃）→ 手動 `/model opus`。

| 情境 | 主對話設定 |
|---|---|
| 日常開發：規劃要準、執行是機械活 | `opusplan`（預設） |
| 執行本身就需要判斷（難根因、邊改邊取捨） | `/model opus` |
| 純機械批次改、規格已完全確定 | `/model sonnet` |

**fast mode（`/fast`）**：不是換模型，是 Opus 換一組偏向低延遲的 API 設定，
最快 2.5 倍、每 token 較貴（Opus 5／4.8 才支援，Sonnet／Haiku 沒有）。
判準：**互動式工作（快速迭代、現場除錯）才開；長時間自動跑的任務不開。**
成本陷阱：一段對話裡第一次開啟時，要用 fast 價付掉**當下整個 context** 的未快取輸入——
所以要開就在 session 開頭開，不要聊到一半才開。訂閱制的 fast mode 走 usage credits，
不算在方案額度內。

**切到 `fable` 的兩個情境**（`fable` 別名＝Claude Fable 5，官方定位是「最難、最長時間的任務」）：

| 情境 | 判準 |
|---|---|
| 制度本身的大改版 | 要同時拿住十幾個制度檔的互動關係做取捨，改一處會牽動別處 |
| 架構決策、需要品味判斷的題 | `judgment.md` 誠實條款判定「此處需要品味判斷」，且三選一裡選了「升級模型」 |

不屬於這兩類就不要切——量大、時間長、覺得難，都不是理由（見 §5 反例）。

**fable 當指揮官時，§5 的階梯倒轉為只降不升**：`opus` 兩輪失敗不再往上派，
由 fable 指揮官親自拍板。用完在該次回報寫一行實際消耗。

## §5 升降級路徑

- **`haiku` 錯 1 次** → 同任務升 `sonnet` 重派（附 haiku 的錯誤輸出當反例）。
- **`sonnet` 同一子任務連錯 2 次** → 升 `opus`，附完整失敗軌跡（兩次的輸入、輸出、錯在哪）。
- **`opus` 解出模式後** → 把解法寫成明確步驟，降回 `sonnet`／`haiku` 批次套用到其餘同類項。
- **同一子任務最多重試 2 輪**（升級也算輪）：仍失敗 → 停，向使用者回報事實、已排除的假設、卡點。
- **`fable` 原則不派為 subagent**，僅使用者明說才用；用後回報實際消耗。
- 層級區分（別跟除錯搞混）：本節的「輪」指指揮官重新交辦 subagent 的次數；
  hard-rules #6 的「2 次沒好進 /debug-protocol、第 3 次停手 revert」指單一 agent
  在自己 context 內的除錯修改次數。兩者各自計數，互不抵扣。
- **反例（量大不等於需要升級）**：要改 40 個檔案的 import 路徑，覺得「量大很難」就升 `opus`
  → 錯，這是機械活，`haiku` 批次做＋抽查即可。

## §6 交辦三要素與派工包

三要素缺一不發：**目標與動機**（做什麼＋為什麼，讓 subagent 能自行取捨細節）、
**驗收條件**（可驗證的完成判準，能寫成指令最好）、**回報格式**（長度上限與結構）。

通用派工包（填空，不要即興寫）：

```
目標與動機：<做什麼>，因為 <為什麼>。
範圍與限制：只准動 <檔案範圍>；遵守 ~/.claude/rules/ 下的常載規則；
  不確定的設計決策先用最簡單解並在回報標註 ASSUMPTION。
驗收條件：<可機械判定，例如「pytest tests/x.py 全綠」>，不是「能動就好」。
回報格式：結論 ＋「檔案:行號」；長產物存到 <路徑> 後只回路徑＋3 行摘要。上限 N 行。
查不到／做不到就直說並回報卡點，禁止編造，禁止交出沒跑過的程式碼。
```

各類任務在此基礎上**各加一句**（模型選擇看 §2，不在這裡重複）：

- **搜尋**：「也要檢查 <別名／舊名／字串引用等變形>；找不到就回『無結果』並列出搜過的 pattern」。
- **實作**：「規格逐條列出；新增測試 <名稱> 且全綠」。
- **重構**：「**不變式**（絕不能變的行為，例如現有測試不改內容且全綠、公開 API 簽名不變）；
  **先跑 <測試指令> 記錄基線**再小步改，每步重跑；任何一步變紅且 2 次內修不回 → 立即
  revert 全部並回報，不要硬推」。
- **研究**：「來源優先序：官方文件 > 原始碼 > 其他；每個結論附出處（URL 或 檔案:行號）；
  區分事實與推測；**禁止用訓練記憶充當查證結果**」。
- **審查**：「你是沒有參與實作的審查者，只依規格與程式碼本身判斷（**不給實作者自述**）；
  verdict（通過／退回）＋問題清單按嚴重度排序；沒把握的標『不確定』」。

## §7 驗證：不自驗

修改者永不擔任自己產出的唯一驗證者。驗證一律派 **fresh-context** agent（乾淨 context，
沒看過實作過程），且驗證 prompt 只給規格、不給實作者的自述：

| 產出類型 | 驗證方式 |
|---|---|
| 檔案／文件 | read-back：叫它讀檔，回答「是否完整、與規格哪裡不符、哪句弱模型會誤讀」 |
| 程式碼 | 實跑：跑測試或走主流程，貼輸出；不接受「看起來正確」 |
| 高風險判斷 | 第二意見：同題派 2 個 agent 各自作答比對分歧；或多答案評審擇優（uplift.md 方法 2） |

驗證 agent 的回報也遵守回報合約：結論 ＋ 檔案:行號 ＋ 修正建議，不整篇重抄。
