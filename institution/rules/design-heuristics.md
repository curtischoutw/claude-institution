## 1. Rule of three（何時抽象）

**判準**：if 同一模式出現第 2 次 → then 忍住，複製並加註 `# duplicated from <位置>`。
if 出現第 3 次 → then 才抽成共用函式/模組（此時你有 3 個真實案例，能看出哪些部分
真的共通）。if 還沒出現第 2 次就想「以後可能會用到」→ 不抽象，YAGNI。

- **正例**：兩處都要 retry 邏輯 → 各自寫，註明重複；第三處出現時抽 `with_retry()`，
  用 3 個案例決定參數（次數、backoff、哪些例外可 retry）。
- **反例**：寫第一個 API client 就先做 `BaseClient` 抽象類 → 只有 1 個案例的抽象
  必然抽錯維度，之後每個新 client 都在跟它打架。

## 2. 先寫呼叫端，再寫實作（API 形狀由使用場景決定）

**判準**：if 要新增公開函式/類別/endpoint → then 先寫 3–5 行「理想中呼叫端長什麼樣」
（可以是測試、可以是註解裡的虛構碼），對這個形狀滿意了才寫實作。

- **正例**：先寫 `user = fetch_user(id, with_orders=True)` 覺得順手 → 據此定簽名。
- **反例**：照資料庫欄位順序定出 `fetch_user(id, include_flags, mode, opts_dict)`，
  每個呼叫端都要傳一堆 None → 形狀由實作方便決定，錯了。

## 3. 資料結構先於邏輯

**判準**：if 程式碼裡出現平行陣列、對同一欄位判空 ≥3 處、或同一個 key 的
`dict.get(k, default)` 散布 ≥3 處 → then 停下來重看資料模型：多半是結構錯了（該用 dataclass、
該正規化、該把可選欄位拆成兩型別）。資料模型對了，邏輯自然變短。

- **正例**：`names[]`、`ages[]`、`emails[]` 三個平行陣列靠 index 對齊 → 改成
  `list[Person]`，三處 zip 邏輯消失。
- **反例**：資料模型不動，再加第 4 個平行陣列和第 4 組對齊檢查。

## 4. 模組邊界跟著「一起變更」切，不跟著名詞分類切

**判準**：if 要拆檔/拆模組 → then 問「哪些程式碼總是在同一個需求裡一起被改？」
一起變的放一起。if 發現每個小需求都要同時動 3 個「分類整齊」的檔案（models.py、
views.py、utils.py 各改一行）→ 邊界切錯了，按功能聚合。

- **正例**：匯出功能的 route、序列化、權限檢查放同一個 `export/` 目錄——改匯出
  只動這裡。
- **反例**：按「工具類統一放 utils.py」歸檔，utils.py 長到 2000 行、每個 PR 都碰它、
  merge conflict 之王。

## 5. 錯誤處理三選一（禁止默默吞）

**判準**：每個 `except` / error branch 必須明確屬於三者之一，選不出來就是還沒想清楚：
1. **就地處理**：這一層有足夠資訊修復或重試 → 處理掉，不往上報。
2. **向上拋**：這一層不知道怎麼辦 → 原樣拋（或包一層加 context），讓知道的人決定。
3. **記錄後降級**：功能非關鍵、失敗可接受 → log warning ＋ 回退行為，且回退行為
   要寫在 docstring。

`except: pass` 與「catch 後只 return None 不記錄」不屬於任何一類，一律禁止
（與 /debug-protocol 禁止事項一致）。

- **正例**：讀取使用者頭像失敗 → 類型 3：log warning、回傳預設頭像，docstring 註明。
- **反例**：資料庫寫入失敗被 `except Exception: return None` 吞掉，呼叫端以為成功
  → 資料默默丟失，最貴的一種 bug。

## 使用強度

以上 5 條在設計時**過一遍當 checklist**（各 ≤30 秒），不是每條都要產出文件。
與設計有關的高風險取捨（兩個方案差很多、影響 ≥1 天）→ 升級用 uplift.md 方法 1/2。
