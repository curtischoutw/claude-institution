# 快速診斷：本 harness 三大耗損源與修法

<!-- 按需引用檔。建立：2026-07-05（Fable 5 session）。供 dispatch.md 與 judgment.md 引用。 -->

## 第 1 名：主對話下場幹粗活（最漏 token）

**症狀**：主對話直接連續 Read 多個檔、Grep 大範圍、貼長指令輸出。每一筆都永久佔據主 context，
還會在後續每次推理中重複計費，並稀釋注意力（失焦的主因也是它）。

**弱模型可照做的修法**：
- 觸發條件（任一成立就派 subagent，不要自己動手）：
  1. 需要讀超過 3 個檔案
  2. 不確定目標在哪個檔（要搜尋、要掃 repo）
  3. 要查網頁或外部文件
  4. 批次修改超過 3 個檔
- 派法：模型選擇一律查 `~/.claude/rules/dispatch.md` 調度表（不要憑印象選），
  交辦格式照 `~/.claude/rules/prompt-templates.md`。
- 回報合約：subagent 只回結論與「檔案:行號」；長產物存檔後只傳路徑。

## 第 2 名：常載檔膨脹與規則只加不刪（最易失焦）

**症狀**：CLAUDE.md 與其引用檔越長，單條規則的服從率越低；規則互相矛盾時弱模型會隨機挑一條。
每個 session 都重複燒這些 token。

**弱模型可照做的修法**：
- 行數預算是硬限制：CLAUDE.md 本體 ≤150 行、其直接 @import 的常載檔合計 ≤500 行。
- 想加一條常載規則之前，必答兩題：(1) 能不能做成 hook（機器強制）？(2) 能不能放進
  按需引用檔或 skill（用時才載入）？兩題都答「不能」才准進常載檔。
- 超限就精簡：把「程序與範例」下放到 `rules/` 按需檔，常載檔只留一行路由。

## 第 3 名：自驗自查與假完成（最易出錯）

**症狀**：同一個 context 裡「寫的人」跟「驗的人」是同一個模型——它已經相信自己是對的，
驗證淪為確認偏誤。輸出「✅ 測試通過」但沒有貼輸出，是最典型的假完成。

**弱模型可照做的修法**：
- 宣稱完成前必走 `/done-check`：每個 ✅ 都要附實際指令與輸出，否則標 ⚠️ 未驗證。
- 重要交付另派 fresh-context 驗證 agent（沒看過實作過程的乾淨 context）：
  - 檔案類 → read-back：叫它讀檔並回答「內容是否完整、與規格哪裡不符」
  - 程式碼類 → 叫它實際跑測試或跑主流程，貼輸出
  - 高風險判斷 → 第二意見：同題派兩個 agent 各自作答，比對分歧點
- 判準：修改者永不擔任自己產出的唯一驗證者。
