## 三件 Curtis 沒問、但我認為最重要的事

1. **額度問題未確認**：Curtis 被告知「某些請求會被安全機制導向 Opus 4.8」，但「被導向的
   請求是否消耗本窗口額度」我在此環境查不到，**未確認**。建議：到 claude.ai 的 usage
   儀表板，發一個明確會被導向的請求前後對照用量，實測一次就有答案。在確認前，調度守則
   一律假設「所有請求都花錢」，這個假設偏保守但安全。

2. **hooks 層（層 0）還是空的**。整套制度目前全靠「模型讀了規則並且服從」，這是最弱的
   強制形式。第一個機器可判定的規則出現時（例如「禁止 commit 含 console.log」「禁止直接
   push main」），就該用 /update-config 做成 hook——那才是弱模型真正逃不掉的規則。
   不要等制度齊全才開始，一條就值得做。

3. **這套制度的複利引擎是 /lesson 的升級迴圈**（犯錯→記錄→第 2 次觸發→升級固化），
   而迴圈最容易斷在「弱模型被糾正後忘了記」。如果你是弱模型 session 且剛被 Curtis 糾正：
   現在、立刻、用 /lesson 記下來，這比你手上的任務更重要——任務只影響今天，lesson 影響
   之後每一天。

## 這套制度最可能的退化方式與預防

| 退化方式 | 徵兆 | 預防 |
|---|---|---|
| 規則只加不刪，常載檔膨脹 | CLAUDE.md 快碰 150 行 | maintenance.md 的精簡門檻是硬限制，照做 |
| 規則被讀到但不被遵守 | 同一條硬規則反覆被違反 | 那條規則放錯層了——升級成 hook 或改寫成更機械的 if-then |
| 型號表過時 | dispatch.md 查證日期超過 3 個月 | 引用前先派 claude-code-guide 重查 |
| lessons.md 積灰 | 條目全是 first-hit，沒有 promoted | 升級迴圈斷了；session 起手式有讀 lessons 嗎？ |
| 驗證流於形式 | 驗證 agent 每次都回「沒問題」 | 驗證 prompt 別給實作者自述；要求它必須列出「最接近出錯的一點」 |
| 制度檔被弱模型好心重寫 | diff 巨大、語氣變了 | maintenance.md 權限分級；發現就從 backups/ 還原 |
