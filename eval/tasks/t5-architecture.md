# t5 — 架構取捨：幫 CLI 加外掛系統（高難 / 規格模糊）

## 任務 prompt

```
我們有一個內部用的命令列工具（目前是單一 Python 檔案，裡面大概 10 個子命令，
例如 `tool.py deploy`、`tool.py status` 這種）。現在想讓外部團隊也能替這個工具
新增自己的子命令，不用改我們的原始碼、也不用等我們 review 合併。

請幫忙設計一套外掛（plugin）系統，讓外部團隊可以自己掛新的子命令進來。

不需要真的寫出完整實作，我要的是設計方案：你會怎麼做、為什麼、有什麼取捨。
```

## 評分 checklist（皆為可觀察行為，無標準答案）

- [ ] 動手設計方案之前，先寫出 3–5 條「好答案的判準」（可驗證的，例如「外部團隊新增
      外掛不需要碰到我方 repo」「載入未知外掛不能讓整個 CLI 崩潰」），而不是先想方案
      再回頭列出方案剛好符合的優點
- [ ] 明確列出做這個設計時用到的 ASSUMPTION（例如「假設外掛都是可信任來源」或
      「假設外掛數量不多、不需要熱重載」），沒有沉默假設
- [ ] 至少提出並比較兩種以上的技術路線（例如 entry_points / 目錄掃描 / 顯式 registry），
      逐條對照前面寫的判準打分，而不是只講一種方案
- [ ] 產出一份決策日誌，格式包含「選了什麼 / 放棄了什麼與為什麼 / 推翻條件」
      （對照 `~/.claude/rules-lib/uplift.md` 方法 5 的格式）
- [ ] 結論附至少一個「可證偽的檢驗」（例如「若六個月後外部團隊平均要等我方 review
      才能上線新外掛，代表這個設計選錯了」），不是寫「應該可以運作良好」這種無法檢驗的話
- [ ] 有主動點出至少一項風險或邊界情況（例如外掛互相衝突、外掛程式碼安全性、版本相容性），
      不是只講方案的優點

## 備註

- 沒有 fixture，也沒有標準答案；評分備註見 `eval/answers/t5-t6-scoring-notes.md`
  （記錄「這題在測什麼」與常見的低分模式，供評分者參考，不是解答）。
- 這題的重點不是「外掛系統設計得多好」，是「面對模糊規格時有沒有走判準先行、
  假設外顯、多方案比較、決策留痕、結論可證偽」這套流程。
