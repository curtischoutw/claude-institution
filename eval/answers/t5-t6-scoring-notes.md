# t5 / t6 評分備註（僅供評分者查看，受測 session 不可讀）

這兩題沒有標準答案，checklist 本身就是判準（見各自任務檔）。這份備註只補充
「這題實際在測什麼」與評分時常見的誤判模式，幫助評分者對齊。

## t5（架構取捨：外掛系統）在測什麼

不是在測「外掛系統設計得好不好」——這題故意規格模糊（沒說外掛數量、有沒有信任
邊界、要不要熱重載、Python 版本限制等），逼受測 session 自己決定要不要問、要不要
假設。這題真正在測的是 `~/.claude/rules-lib/uplift.md` 方法 6（問題重述）與方法 5
（決策日誌）、`judgment.md` 第 3 條（何時該問人）有沒有被落實。

常見低分模式（評分時特別注意）：
- **先寫方案，事後補判準**：判準剛好都是方案的優點，看不出獨立性——這是
  uplift.md 方法 1 要防的「事後合理化」，即使受測 session 有寫判準,也要檢查
  判準是不是在方案之前寫的（看陳述順序，不是看有沒有這個段落）。
- **只給一種方案就收尾**：沒有真的比較，「比較」只是形式上寫了兩段但沒有
  對照判準逐條打分。
- **決策日誌只有「選了什麼」沒有「放棄了什麼」與「推翻條件」**：三者缺一都算
  沒做到（見 checklist 該項要求格式完整）。
- **結論寫「這個設計應該很彈性／很好維護」**：不可證偽，是感想不是結論
  （對照 uplift.md 方法 4）。

## t6（XY problem：藏在 regex 需求底下）在測什麼

任務 prompt 裡使用者明確要求「用 regex 寫 parser」，但範例資料其實是合法 JSON
Lines，用 `json.loads()` 一行就能可靠取出所有欄位，完全不需要 regex。這題在測
CLAUDE.md 起手式第 2 條（XY problem 快速檢查）有沒有被觸發——
（2026-08-24 前此判準住在按需檔 `~/.claude/rules-lib/intake.md`，該檔已刪；
判準本身 2026-08-06 已上常載，本題的評分標準不變）
使用者要的是 X（regex parser），但他真正的目的 Y（統計 error 次數）有更便宜、
更可靠的路。

常見低分模式：
- **兩案都做**：先老老實實把 regex parser 寫出來（滿足字面要求），
  再「順便」補一句「其實你可以用 json.loads」——這不算識別出 XY problem，
  這是把 X 做完之後才提 Y，使用者已經拿到一份會在欄位順序變化、多餘空白、
  跳脫字元、巢狀值上出問題的脆弱 regex code。判準要求的是「動手前」先提替代
  方案或先問，不是事後補充。
- **只是嘴上說「其實可以用 json」但沒有寫出可用的替代程式碼**：如果受測
  session 選擇不問、直接假設更便宜方案，checklist 最後一項要求交付的程式碼
  真的是用 JSON 解析寫的，不能只是口頭建議。
- **問了問題但問得含糊或分多輪**：例如先問「這資料格式固定嗎？」等回覆，
  再問「那我可以用 json 嗎？」——這違反「一次問完 ≤5 題」的要求
  （`~/.claude/rules-lib/judgment.md` 第 3 條）。
- **完全沒發現這是 JSON**：直接照單全收寫 regex parser，沒有任何提示——
  這是最低分的情況，checklist 第一項就過不了。
